# 技术方案：求职意向模块

## Context

当前 job 表无 `biz_type` 字段，招聘/求职数据完全混同，导致：
- 求职数据无法被任何接口独立查询
- `HomeTop/HomeFeed` 硬编码跳过 bizType≠1 的请求，求职 Feed 返回空
- `CountByUser` 不区分类型，导致招聘/求职共享上限计数
- `ListByUser`（"我发布的"）的 `bizType` 参数传入但 SQL 里完全没使用

方案目标：在现有 job 领域内完成全部改动，不引入新表/新 Handler/新 Wire 注册，用 `biz_type` 字段在每一层做分支过滤，打通求职意向完整的 CRUD + 浏览 + 置顶 + 刷新链路。

---

## 架构决策（已确认）

- 招聘（type=1）与求职（type=2）共用 job 表，加 `biz_type` 字段区分
- 字段差异处理：`company_name` 求职时为空字符串，`longitude/latitude` 求职时置 0（城市级别由 area_id 字段表达）
- 路由全部复用 `/jobs/*`，biz_type 通过请求体传递，Router 层零改动
- 历史数据：AutoMigrate 时 `DEFAULT 1` 自动回填，无需手动 UPDATE

---

## 改动清单

### 1. internal/model/job.go
在 `Job` struct 末尾追加一个字段：
```
BizType int `gorm:"column:biz_type;default:1"`
```

---

### 2. internal/server/migration.go
在 `m.db.AutoMigrate(...)` 参数列表中追加 `&model.Job{}`，触发 ADD COLUMN。

---

### 3. api/v1/job.go

**(a) `JobCreateRequest`**
- 新增 `BizType int` 字段，`binding:"required,oneof=1 2"`
- `CompanyName` 去掉 `binding:"required"`（求职无企业名称）
- `Longitude`、`Latitude` 去掉 `binding:"required"`（求职无需精确坐标）
- `Address` 去掉 `binding:"required"`（求职填意向城市，用 area 字段表达即可）
- 在 handler 层根据 biz_type 做条件校验（type=1 时上述字段必填）

**(b) `JobFilter`**（`JobListRequest` 的子结构）
- 新增 `BizType int` 字段（0=不限，1=招聘，2=求职）

**(c) `JobListItem`**（列表/详情响应体）
- 新增 `BizType int` 字段，供前端区分展示

---

### 4. internal/service/job.go

**(a) `JobCreateInput`**
- 新增 `BizType int` 字段

**(b) 在 service 包内定义本地常量**（不得 import api/v1，避免分层违规）
```go
const (
    bizTypeRecruit = 1
    bizTypeResume  = 2
)
```

**(c) `Create()` — 修复两处 bug**
- 上限检查：调用 `CountByUser` 时传入 `input.BizType`；limit 按 biz_type 分支（招聘=10，求职=5）
- 构造 model.Job 时追加 `BizType: input.BizType`

**(d) `HomeTop()` — 修复硬编码**
- 删除 `if bizType != 0 && bizType != 1 { return 空 }` 的提前返回
- 直接透传 `bizType` 给 `jobRepository.ListTop(ctx, bizType, limit)`

**(e) `HomeFeed()` — 同上修复**
- 直接透传 `bizType` 给 `jobRepository.ListFeed(ctx, bizType, pageNum, pageSize)`

---

### 5. internal/repository/job.go

**(a) `JobListQuery` struct**
- 新增 `BizType int` 字段

**(b) `JobRepository` 接口 — 3 处签名变更**
```go
CountByUser(ctx, userID int64, bizType int, status model.JobStatus) (int64, error)
ListTop(ctx, bizType, limit int) ([]*model.Job, error)
ListFeed(ctx, bizType, pageNum, pageSize int) ([]*model.Job, int64, error)
```

**(c) 各方法实现 — 统一增加 biz_type 过滤（BizType > 0 时才加条件）**

| 方法 | 改动 |
|------|------|
| `List()` | WHERE 块追加 `if query.BizType > 0 { db = db.Where("job.biz_type = ?", query.BizType) }` |
| `ListByUser()` | 修复 bizType 参数未使用的 bug，追加同样的 WHERE 条件 |
| `CountByUser()` | 签名加 bizType，追加 WHERE 过滤 |
| `ListTop()` | 签名加 bizType，追加 WHERE 过滤 |
| `ListFeed()` | 签名加 bizType，追加 WHERE 过滤 |

注意：`ListTop` 现有查询已有严格的置顶时间窗口过滤，加 biz_type 后求职置顶数据可正常参与排序，无副作用。

---

### 6. internal/handler/job.go

**(a) `Create()`**
- 条件校验：`req.BizType == 1` 时检查 `CompanyName`、`Longitude`、`Latitude`、`Address` 非空（替代去掉的 DTO binding）
- 构建 input 时追加 `BizType: req.BizType`

**(b) `List()`**
- 构建 `repository.JobListQuery` 时追加 `BizType: req.Filter.BizType`

**(c) `buildJobListItem()`**
- 构建 `v1.JobListItem` 时追加 `BizType: job.BizType`

---

### 7. internal/router/job.go — 无改动

所有路由复用，biz_type 由请求体携带，路由层完全透明。

---

### 8. cmd/server/wire/wire.go — 无改动

无新 Handler/Service/Repository 注册。

## 历史数据兼容性

| 场景 | 处理 |
|------|------|
| 已有 job 记录 | AutoMigrate DEFAULT 1 自动回填，全部视为招聘，零破坏 |
| 招聘上限检查 | CountByUser 过滤 biz_type=1，精确计数，不受影响 |
| 首页 ListTop/ListFeed（type=0 全部） | biz_type=0 时不加过滤条件，历史招聘数据正常返回 |
| 求职 Feed（type=2） | 历史无 biz_type=2 数据，新发布后立即可查 |

---

## 验证方式

1. 执行 `make migration` 确认 job 表新增 biz_type 列，历史行默认值为 1
2. 发布招聘（biz_type=1）：`POST /jobs/create` 带 company_name + 坐标，正常入库
3. 发布求职（biz_type=2）：`POST /jobs/create` 不带 company_name/坐标，正常入库
4. 求职上限校验：连续发布 5 条 biz_type=2，第 6 条返回 `ErrJobLimitExceeded`
5. 求职列表：`POST /jobs/list` 传 `filter.biz_type=2`，只返回求职数据
6. 招员工首页 Feed：`POST /home/feed` 传 `type=2`，返回求职意向（修复前返回空）
7. "我发布的"求职标签：`POST /jobs/my` 传 `biz_type=2`，只返回当前用户的求职意向
8. 求职置顶：对 biz_type=2 的 job 发起 `/jobs/top`，支付后 `top_start/end_time` 正确写入
